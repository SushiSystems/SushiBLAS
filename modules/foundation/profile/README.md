# profile

The one front SushiBLAS writes profiling through: the `SB_ZONE` macros, the level a translation unit compiles in and the names the library puts into a record. Its headers are included as `<SushiBLAS/profile/<name>.hpp>`.

It depends on no module of this repository and on SushiProfiler, which no module below [`profiling`](../../engine/profiling/README.md) includes. With `SB_ENABLE_PROFILER` off the macros expand to nothing and the module needs no SushiProfiler header.

| File | Declares |
| --- | --- |
| `profile_config.hpp` | Generated by the build from `profile_config.hpp.in`: `SB_ENABLE_PROFILER` and `SB_PROFILE_LEVEL` |
| `profile_gate.hpp` | `Internal::Profile::K_COMPILED_LEVEL`, the level of one translation unit, from the two settings |
| `profile.hpp` | `SB_ZONE`, `SB_ZONE_FINE`, `SB_ZONE_DETAIL`, `SB_VALUE`, `SB_COUNTER`, `SB_INSTANT`, `SB_LOCK_WAIT` |
| `profile_keys.hpp` | The group name and the `sushiblas.*` fact names |

## Levels

`SB_PROFILE_LEVEL` is 2 in every build type unless the configure step sets another; the header is generated, and `profile.hpp` neither defines nor defaults either setting. `profile.hpp` is included from `.cpp` files and from the profiling and benchmark modules only. A zone has a level and compiles in when its level is at most the translation unit's: `SB_ZONE` is level 1, `SB_ZONE_FINE` level 2, `SB_ZONE_DETAIL` level 3. No zone of level 3 exists yet. A zone compiled out is an empty object, and a value, counter or instant compiled out is a statement that evaluates nothing, so a variable only a macro reads is not reported unused.

`K_COMPILED_LEVEL` has internal linkage, so two translation units compiled at different levels in one program do not meet. The tests build one of each: a translation unit that includes the generated header, undefines a setting and defines its own.

## Names

Spans carry two attributes, `flops` and `bytes`, which SushiRuntime's device source writes from the node's `NodeCost`. Their names are SushiProfiler's (`SushiProfiler::DeviceSpanKeys`), so this module does not repeat them. The facts that state a device's ceilings are built by [`profiling`](../../engine/profiling/README.md) from the same header.

## Not in this module

The contributor that states the facts, the ceilings file and `register_profiler_parts` live in [`profiling`](../../engine/profiling/README.md). The cost of an operation is [`cost`](../cost/README.md)'s.
